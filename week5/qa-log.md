# 第 5 周 Q&A 记录

## Q1（11-09）为什么说 attention 的 q·k / 句向量点积大就代表"相关"？
- 点积 = 每个维度相乘再相加：两个向量在同一维度上都大，贡献才大；一正一负就会扣分。几何上 a·b = |a||b|cosθ，量的是方向一致不一致。
- 点积本身不懂"相关"，是**训练**让它有了这个意思：
  - attention：q=xWq, k=xWk，如果"it 关注 animal"能让 loss 下降，反向传播就把 Wq、Wk 往"q_it·k_animal 变大"的方向调。
  - bge：用对比学习训练，配对的问答句点积要高，随机配的句子点积要低。
- 推论：模型只认得训练里见过的那种"相关"，遇到领域黑话可能失灵，所以要做评测（L4）。

## Q2（11-09）bge 是用问答对训练的吗？大模型也是这样吗？
- bge 三步：① 在大量文本上预训练 ② 用上亿对弱配对（标题↔正文、问题↔回答、搜索词↔被点击的网页）做对比学习 ③ 用精标的问题↔段落 + 难负例微调。
- 对比学习的 loss = 对"问题和一批段落的相似度"做 softmax + 交叉熵，正确答案是配对的那个段落（和第 3 周预测下一个字是同一个公式）。
- 大模型：预训练（预测下一个 token）→ SFT（问题→回答，逐 token 学着写出回答）→ RLHF/DPO。
- 区别：两者都用问答对，但 bge 学"找"（向量靠近），大模型学"写"（生成文字）。RAG 正好是这个分工：bge 检索，LLM 生成。

## Q3（11-09）向量数据库是不是把非结构化文件变成了结构化数据？
- 对的一半：非结构化文本第一次能统一成定长数字，按"意思"检索。
- 纠正：向量 ≠ 结构化。每一维没有可解释的含义，没法写 WHERE 条件，唯一的操作是"找最像的"；而且有损，还原不回原文，所以原文要一起存。
- 准确说法：向量库是给非结构化数据建的"语义索引"，不是替代原来的存储。一条记录 = id + 向量 + 原文片段 + 元数据（元数据才是结构化的，可以和向量检索组合做过滤）。
- 向量库多出来的核心能力：近似最近邻搜索（HNSW），在上亿条里毫秒级找出 top-k。
- 售前说法：文档不用迁移，只建索引；已有 PostgreSQL 就可以用 pgvector 起步。

## Q4（11-09）"长度大的文档占便宜"，跟向量长度有关系吗？
- 三种"长度"：维度（bge 固定 512，和文本长短无关）、模长 |v|、文本字数。之前说的"长"指的是模长。
- 字袋法：文本越长，计数越大，模长越大（"退款"=(1,1)，"退款退款退款"=(3,3)，方向相同，点积变成 3 倍，cos 不变）。所以不 normalize，长文档就会占便宜。
- bge：模长和文本长度没有简单的比例关系，但各句也不一样长，所以统一 normalize，只比方向。
- 真正和文本长度有关的是切块：块太长会混进多个话题，向量变成"平均"，跟哪个问题都不特别像；块太碎又会信息不全。

## Q5（11-09）[CLS] 是什么？
- classification 的缩写：分词器自动加在句首的特殊 token，本身没有字面意思。"快递到哪了" → [CLS] 快 递 到 哪 了 [SEP]。
- bge 是 Encoder（BERT 一类），不加因果 mask，每个位置都能看到整句。[CLS] 经过每一层 attention（bge-small-zh 是 4 层，BERT-base 是 12 层） 收集全句信息，再用对比学习专门优化这个位置，于是它就成了句向量（像会上专门做记录的人）。
- 其他取法：平均池化；Decoder 模型取最后一个 token（因为有 mask，只有它能看到全句）。用哪种要和模型训练时的做法一致。
- 追问：三种取法画图解释，见交互图 https://claude.ai/artifact/BCoTRA5F6ptCwTPf8yiHnX（week5/pooling-demo.html）。关键在 attention 能看到谁：Encoder 每个位置都能看全句（取 [CLS] 或取平均都行）；Decoder 有因果 mask，只有最后一个 token 看全了整句，所以取最后一个。

## Q6（11-09）[CLS] 每一层是怎么"总结"的？
- 第 0 层：[CLS] = 固定的词向量 + 位置 0 的向量，每句话都一样，什么都不知道。
- 每层三步（和第 3 周一样）：q_cls 和所有 k 做点积 → softmax 得到权重 → 对 v 加权求和，加上残差，再过 FFN。"总结"= 加权平均。
- 叠多层：下层的字已经吸收了上下文（"递"变成了"快递"），上层的 [CLS] 收集到的就是词级、再到句级的意思。多头 = 同时关注不同的东西。
- 看谁、看多少，由 Wq/Wk/Wv 决定，这些都是训练出来的。
- 纠正：bge-small-zh-v1.5 是 4 层、512 维、8 头（不是 12 层）。用公式验证：12·4·512² + 21128·512 ≈ 2340 万参数 × 4 字节 ≈ 94MB，和下载大小对上了。

## Q7（11-09）stdio 只能用于本地 MCP？HTTP 可以远程？
- 对。stdio：Client 把 Server 当子进程启动，必须在同一台机器，一对一，天然隔离。Streamable HTTP：Server 独立部署，通过网址连接，多个客户端共用，必须做鉴权（OAuth）+ HTTPS。SSE 是旧的传输方式，已被 Streamable HTTP 取代。
- 改成远程只要两行（mcp 2.3）：server 用 `mcp.run(transport="streamable-http", port=8000)`；agent 用 `Client("http://localhost:8000/mcp")`。工具代码不变。
- 售前：企业知识库做成远程 HTTP MCP Server，部署在客户自己的云上、挨着数据，各种 agent 共用，权限统一在 Server 层管。

## Q8（11-09）大模型是怎么知道要去找 tool 的？
- 模型不"知道"，它只是在预测下一个 token。
- ① tools 列表会被服务端拼成文字放进 prompt（工具名 + description + 参数），对模型来说和其他文字一样。
- ② SFT/RL 训练里看过大量"工具列表 + 问题 → 输出调用格式"的示范，所以问题和 description 对得上时，它预测出的就是调用格式的 token。
- ③ API 把这串格式解析成 tool_calls；真正执行的是 agent 代码（模型自己只会生成文字，所以去掉 stop 会编出 Observation）。
- 实用结论：选哪个工具主要看 description 写得好不好；system prompt 可以加强这个信号；工具太多容易选错，要控制数量或先筛选。
- 追问：工具是我自己写的，模型训练时见过吗？没见过具体工具，但练过"读工具说明书"这项通用能力：训练数据里有大量各式各样（很多是人造）的工具，学到的是"问题对上 description 就选它，按 schema 填参数，都对不上就不调用"。好比会看遥控器上的标签，就能用没见过的空调。和 RAG 是同一种能力，叫上下文学习（in-context learning）：RAG 是现场读资料，tools 是现场读说明书。局限：description 含糊、两个工具很像、参数名奇怪，都会导致用错，所以写 description 是一项工程活。

## L3 练习观察（11-09）
- 复合问题被拆成多次检索，query 像关键词 = 查询改写（query rewriting），这是 Agentic RAG 的好处；风险是改写时可能丢掉上下文。
- 闲聊不检索，是模型按 system prompt 自己判断的。固定 RAG 每问必查，闲聊会得到"知识库里没有"。
- 取舍：固定 RAG 便宜、快、可预测；Agentic RAG 会拆问题，但更慢更贵，而且可能该查的时候不查（最危险，要靠评测发现）。

## Q9（11-09）Agentic RAG 一定会把 query 改写成关键词吗？
- 不一定。这是模型从"网页搜索工具"的训练示范里学来的习惯，它并不知道背后是语义检索。
- bge 是用完整问句训练的，完整问句往往比关键词更准（关键词会丢掉意图，比如"几天"）；BM25/ES 这类关键词检索则适合关键词。query 写法要匹配检索器类型。
- 控制方法：在 search_kb 的 description 里写明"query 写成完整问句，保留意图"。
- 不用 agent 的改写技巧：multi-query（改写成多种说法分别检索再合并）、HyDE（先写假答案，用它去检索）、混合检索（关键词 + 向量）。效果好不好，用 eval.py 量。

## L4 练习观察（11-09）
- "AccessKey 传到 GitHub" 没排第 1：bge-small-zh 对英文的理解弱（英文被拆成碎片）；文档写的是"代码仓库"，要对上需要常识。对策：混合检索、换 bge-m3 这类多语言模型、在文档里补同义词。
- 关键词检查判错 1 道（模型换了说法），LLM 裁判判对：实际项目里关键词做初筛 + LLM 裁判复核，两者不一致的再人工看。
- 门槛扫描（bge-small-zh，16 题）：0.50 → 12/12 放行、2/4 挡住；0.55 和 0.60 → 10/12、4/4；0.70 → 只放行 2/12。选 0.55。客服场景答错比说"不知道"更糟，所以宁严勿松；门槛是业务决策。分数在 0.50～0.55 重叠，单靠门槛分不干净，prompt 是第二道防线。16 题样本太小，小心过拟合测试集。
