# 第 7 周 Q&A 记录

## 复习：LLaMA 最大的变化是不是"用 cos 表示位置表 + FFN 函数不同"？（2026-11-12）
- 大方向对，但 RoPE **没有位置表**：不往词向量上加东西，而是在每层注意力里把 q、k 按位置旋转（用到 cos/sin），q·k 只看相对距离。
- 用 sin/cos 做位置表加到词向量上，是 2017 原版 Transformer 的做法，和 RoPE 不同。
- 完整版按重要性：① RoPE ② SwiGLU（3 个矩阵）③ GQA（KV Cache 1/4）④ RMSNorm、去偏置、输出头不共享、词表变大。
- 一句话："骨架没变，改的都是让同样算力效果更好、推理更便宜。"

## L1：搬运受限是不是"把参数从显存搬到 GPU 计算资源"？
- 对。显存 HBM（80GB，远，2TB/s）和片上 SRAM（几十 MB，快，紧挨 Tensor Core）都在 GPU 里；只能算 SRAM 里的数。
- 仓库 vs 工作台：每个 token 都要把每层 W 从 HBM 搬上来算完扔掉，下个 token 再搬，因为 SRAM 放不下 14GB。
- 补充：每步还要读 KV Cache；这是 decode（一次 1 个 token）。prefill 整段一起算 → 算力受限。首字延迟（TTFT）和吐字速度是两个瓶颈。

## prefill 算力受限、decode 搬运受限？
- 对。但原因不是"context 用了所有参数"（两阶段都用全部参数），而是**一次搬运被几个 token 共用**：prefill 2000 token 共用 → 强度≈2000 > 156；decode 每请求 1 个 → 强度≈1（除非凑 batch）。
- 7B/A100：prefill 2000 token ≈ 2×7e9×2000/312e12 ≈ 90ms（实际 ~150ms）；decode 每 token 14GB/2TB/s = 7ms。
- TTFT（首字延迟）看 prefill：FlashAttention、分块 prefill。TPOT（每 token 时间）看 decode：batching/vLLM、量化、GQA、投机解码。

## 屋脊点是不是显卡一次调用参数最多能处理的 token 数？
- 接近，但是"免费的上限"，不是"最多"。屋脊点 = 算力/带宽 = 312e12/2e12 = 156 运算/字节；fp16 decode 强度≈batch，batch=156 时搬权重时间 = 计算时间。
- batch<156 加 token 几乎免费；=156 性价比最高；>156 仍可处理，只是每步变慢。
- 屋脊点是显卡属性，换成 token 要看精度：int4（0.5 字节）batch≈39 就到。
- 实际常被显存（KV Cache 能放几路）卡住，凑不到 156 → L3 vLLM。

## batch 是什么意思？
- 同一步里一起算的 token 个数；decode 时基本 = 同时在聊的用户数。
- 3 个用户各自的当前向量叠成 3×4096 矩阵 x，一次 x@W，W 只搬一次，每人得到一个新字。
- 公交车比喻：开一趟成本固定（搬一次 W），坐 1 人还是 50 人都要开；屋脊点 = 坐满人数。
- 训练时的 batch（多样本一起算梯度）是同一个"多行叠成矩阵"思路。

## 4090 为什么这么厉害？
- 新架构（Ada, 2022），纯算力 165 TFLOPS，是 A100 一半多，价格零头。
- 但推理吃带宽和显存：4090 24GB / 1 TB/s vs A100 80GB / 2 TB/s → 7B fp16 单用户 71 vs 143 token/s；13B fp16 装不下；无 NVLink。
- 屋脊点高（165）是因为带宽小，不是更强：需要更大 batch 才喂饱，却放不下那么多 KV Cache。
- 售前：4090 适合个人开发/7B~13B 量化/小并发 demo；生产用数据中心卡（协议也限制游戏卡进机房）。

## L2 练习点评要点
- 补救系数：第 2 步 e^(1−3)=0.135，第 4 步 e^(3−4)=0.368；m 是目前最大分数（一个数），不乘 v，乘 v 的是 o。
- 不补救最大差 ≈0.36（输出最大 0.48）：新旧 e 基准不同，像人民币和美元直接加。
- Bc=1/16/256 结果都一样（~1e-16），只改顺序；Bc 受 SRAM 限制，常用 64~128。
- FlashAttention 不让模型更聪明，也**不减少 KV Cache**；省中间分数表的显存和搬运（32K 每头 2GB），注意力快 2~4 倍。

## Bc 到底是什么？
- 每块里几个 token 的 K、V（c=column，T×T 表的列）。所有 token 都做 Flash，Bc 只决定一口吃多少。
- T=256、Bc=32 → 8 块；每轮 Q(256×64) × 一块 K(32 个 token) → 256×32 小分数块，用完扔。
- 读书比喻：每次拿 32 页到桌上，内容不变所以结果不变；桌子（SRAM）决定一次摊几页。
- Bc=128、d=128、fp16：K 块 32KB + V 块 32KB，塞进一个 SM 的 SRAM（A100 ~192KB）。真实实现 Q 也切块（Br）。

## 这里不是算 q·k 吗，v 干嘛的？
- 注意力三步：q·k → 分数（看谁）；softmax → 权重；权重 × v 求和 → 输出（拿走的内容）。搜索比喻：k 标题用来匹配，v 正文才是带走的。
- flash.py 每块：Sj = Q@Kj.T → Pj = exp(Sj−m) → O = O*scale + Pj@Vj。K 块和 V 块是同一批 token，分数一出生就去加权 v，然后扔掉 → 不用存 T×T 表。

## SRAM 里完成的计算有哪些？
- 读入：一块 Q（读一次留着），每轮一块 K、V。
- SRAM 内：S=QKᵀ/√d → 行最大值、m、补救系数 → P=e^(S−m) → 更新 l → O=O×scale+P·V → 最后 O÷l。注意力全部计算都在 SRAM。
- 写回：只写 O（训练时再存每行 m、l，反向时重算分数而不存大表）。
- HBM 只看到 Q、K、V 进，O 出；普通版 T×T 表来回 4 趟。

## 一次完成多少 token？Q K V 怎么进去，Q 和 K 都要切？
- Q/K/V 先由普通矩阵乘 x@Wq 等算出，存在 HBM；Flash 只负责按块切着读。
- T=4096、d=128、Br=Bc=128：Q 切 32 块（为了分工），K/V 切 32 块（为了塞进 SRAM）。
- A100 有 108 个 SM（工人），各约 192KB SRAM。每个工人领一块 Q（128 个 token），依次搬 32 块 K/V，完成后写回 O。一次任务 = 128 个 token；32 头 × 32 块 = 1024 任务，约 10 轮。
- 因果遮罩：跳过未来块，计算省约一半。
- decode：Q 只有 1 个 token，把长 K/V 切给多个工人扫（Flash-Decoding），再用 m、l 补救公式合并。

## （看完 15 步 walkthrough 后）prefill 是"理解"的意思吗？这里也有遮罩吗？
- prefill = 预填充：把提示词每个 token 每层的 K、V 算出来填满 KV Cache，顺便出第 1 个词。可粗略理解为"读懂提示词"。
- 有因果遮罩：① 训练就是只看前面，推理要一致；② KV Cache 成立的前提——k3、v3 只取决于 token 1~3，以后永远不变，算一次存起来。若能看后面，每来新词都要重算。
- decode 不需要遮罩：q9 最新，k1~k9 全是过去或自己。
- BERT 无遮罩（理解型），所以不能这样逐词生成 + 缓存。

## BERT 是啥模型？
- Google 2018，Transformer 编码器那一半；GPT 是解码器那一半。第 5 周用的 bge-small-zh-v1.5 就是 BERT 结构（CLS、pooling）。
- 训练：完形填空（遮 15% 的词猜）；双向注意力，每个词看整句 → 理解好（"苹果手机"例），但基本不能生成。
- GPT 赢在生成能统一所有任务 + 越大越好；BERT 类现在主要做 RAG 的 embedding、reranker。
- 售前：RAG 方案里 BERT 类负责检索，GPT 类负责生成。

## token 5 不用把前面 1234 拿回来看了吗？
- 要看！分清"看"和"重算"：看 = q5 与 k1~k5 算分数、按权重拿 v1~v5（每次都做，要从仓库搬 k、v）；重算 = 再拿 x1~x4 乘 Wk、Wv（不用，缓存里的不变）。
- walkthrough 第 7 步（工人 1 搬 token 1~4 的 K/V）、第 11 步（q9 看整个 KV Cache）。
- 开会笔记比喻：笔记写一次不改，新人要翻完所有笔记。decode 每步读整个 KV Cache → 越往后越慢越占显存 → L3 vLLM。

## Flash-Decoding 里工人 2 不是要等工人 1 算完前面的吗？
- 不用等，同时算。q9·kᵢ 只取决于 q9 和 kᵢ，开始前都在仓库里。
- 唯一联系是 softmax 的除以总和：各自算 (m,l,o) 不除，最后用 e^(m自己−m全局) 换算再相加、统一相除。例：(4.0,1.583,55.53) + (3.5,1.533,114.26) → 49.67。
- 两人同时数两个投票箱再相加；补救 = 汇率换算。L2 一维例子是顺序扫，但顺序/分段不影响结果。
- 真正要等的：token 之间（第 10 个等第 9 个）、层之间。

## 补救是根据工人（SRAM）来的吗？SRAM 大小决定 KV 分多少块？
- 两层补救：① 工人内部（FlashAttention 本身）：每搬一块 K/V，最大值变大就补救；Bc ← SRAM 大小（还受 d 影响，常用 64/128），块数 = 长度 ÷ Bc。② 工人之间合并（只有 Flash-Decoding）：切几段 ← 想用几个工人并行，和 SRAM 无关。
- 例：decode KV 32768 token，Bc=128 → 切 64 段 × 512 token 给 64 个工人；每人分 4 块搬、内部补救最多 4 次；最后合并 64 份 (m,l,o)。
- 同一个公式：一个人分批看 vs 多人分头看。

## 串流水线：算 QKV 在 SRAM 吗？卡在算力？QKV 存哪？切 KV 切什么？softmax 用了 Flash？
- Tensor Core 是计算器，SRAM 是旁边的桌子，只能算桌上的数：HBM → SRAM → Tensor Core → 写回 HBM。Wq 一层 32MB 也放不下，普通矩阵乘也切块搬（同 Flash 思路）。
- "要搬"卡的是搬运。8 个 token 强度 8 < 156 仍搬运受限；2000 个 token 才算力受限。
- Q、K、V 写回 HBM；K、V 留作 KV Cache，Q 用完就丢。
- 切的是一层一个头里所有 token 的 K、V，按 token（行）切，每块是几个 token 的完整向量。
- FlashAttention = 整个注意力（q·kᵀ → ÷√d → softmax → ×v）融合在桌上做完；QKV 投影、Wo、FFN 是普通矩阵乘。
- 一层流程：RMSNorm → x@Wq/Wk/Wv（K、V 进缓存）→ RoPE → FlashAttention（只写 O）→ O@Wo + 残差 → FFN + 残差。

## KV 进缓存是 SRAM 吗？长提示词后面 token 在等吗？每层 KV 都要切吗？
- KV Cache 在 HBM。SRAM 全卡约 20MB，13B 一路 4K KV 就 3.2GB。"缓存" = 存起来以后用，不是高速缓存；SRAM 是临时工作台，任务完就清空。
- 提示词所有 token 叠成矩阵一起算，每层同进同出；算力受限 = 整个 prefill 变慢（2000 token ~150ms，2 万 ~1.5s+）。真正等的是别的用户的 decode → vLLM chunked prefill（L3）。
- 每层都算：每层用自己的 Wq/Wk/Wv 算自己的 K、V 存缓存，每层每头的 FlashAttention 各自切块。KV Cache 公式里 "× 层数" 就是这个原因。

## Flash 没有分数表写显存，但 KV Cache 要写，分工时不是还要反复搬 KV 吗？（晕了）
- 对：K、V 还要搬且会重复搬。Flash 消灭的是分数表的搬运，不是 K、V 的。
- T=32K、d=128、一头 fp16：写 KV Cache 两者都一次；读 K、V 普通 16MB，Flash 每块 Q 读一遍最多 ~2GB（多数命中 L2）；T×T 表普通 2GB × 4 趟 = 8GB，Flash 0。
- K、V "瘦"（T×128，线性），分数表 "胖"（T×T，平方）。Flash 用"K、V 多读几遍"换"T×T 表不进显存"，T 越长越划算 → 快 2~4 倍，显存每头省 2GB。

## 我的总结（经修正）
1. token 进来先用普通矩阵乘算 q、k、v；W 太大 SRAM 放不下，切块搬着算。
2. q、k、v 写回 HBM，k、v 留作 KV Cache。
3. 算注意力时多个工人（各带 SRAM）并行，各自分块搬 K、V，最后用补救公式拼对。
4. 一个工人负责"某个头里几个 token 的完整 128 维 k、v"——按 token（行）切，不切向量；一个 token 的 4096 维分到 32 个头是多头的事，不是 Flash 切的。

## 一个 SRAM 负责一个头"维度不变切行数"的 KV？计算过程啥样，token 先乘 q 吗？
- 维度不变切行数：对。工人拿一个头里连续几行（几个 token）的完整 128 维 k、v。
- "第二个工人接着切 K/V、最后合并"是 decode（Flash-Decoding）；prefill 按 Q 分工，每人自己扫完所有 K/V 块，不用跨工人合并。
- token 不是乘 q，q 是乘出来的：① q=x@Wq，k=x@Wk，v=x@Wv；② q2·k1=0，q2·k2=1.1(≈ln3)；③ softmax → 0.25、0.75；④ 0.25×4+0.75×8=7 —— 就是复习第 1 题。
- FlashAttention 做 ②~④；之后乘 Wo、过 FFN，进入下一层。

## prefill 按 Q 分工为啥不用合并？K 不也切开了吗，softmax 咋知道？
- softmax 按行做（每个 query 一行），行与行互不相干。
- prefill 按行分工：工人 1 领 q1、q2 两行，自己把 K 块从左扫到右，整行都是自己看的；最大值变了在自己桌上补救，扫完除以 l。别人没碰这两行 → 不用合并。
- decode 只有 q9 一行，多人干只能按列切这一行 → 各自 l 不是整行总和 → 必须合并。
- 改卷子比喻：prefill 每个老师改完整份卷子；decode 一份卷子拆给两个老师，最后加分。

## （看完 prefill 全过程图后）q k v 计算时用不到 Flash 吧？
- 对。q、k、v 是普通矩阵乘法（h@Wq），也切块搬，但：① 没有 softmax，分块结果直接相加，不需要补救；② K、V 本来就要写回当缓存，且是"瘦"的 T×d。
- FlashAttention 只管 q·k → ÷√d → softmax → ×v；QKV、Wo、FFN 都是普通矩阵乘。
- 图：prefill 全过程 https://claude.ai/artifact/2jwhZAXTE3qWFVNA7rWFL6 ；Q K V 怎么搬 https://claude.ai/artifact/GjFT4JC4KqdkfLM2udvX62

## Flash 还是没懂，步骤全是公式 → 拆到最细（只看一行）
- 图：https://claude.ai/artifact/BtrJFR2bGJX88zPLNJZRi6 （week7/flash-one-row.html）
- 核心一句话：答案 = (Σ e^s·v) ÷ (Σ e^s)，分子 o、分母 l 都是加法，可以分批加，最后除一次。分数 [1,3,0.5,4]、v [10,20,30,40] → 33.68。
- 补救的来由：e¹⁴ ≈ 120 万 > fp16 上限 65504，要减最大值；Flash 先用"目前最大"当尺子，尺子 13→14 时旧的 l、o 乘 e^(13−14)=0.368 换算，答案不变。

## "softmax 分子分母都是加法，可以分批加，最后除一次"解释解释
- GPA 比喻：GPA = Σ(学分×成绩) ÷ Σ学分，每学期往两个总数里加，毕业时除一次。学分 = e^分数，成绩 = v。
- 普通：每项都除以同一个 79.05 → 提到外面 = (2.72×10 + 20.09×20 + 1.65×30 + 54.60×40) ÷ (2.72+20.09+1.65+54.60)。
- Flash：第 1 批 o=428.9、l=22.80；第 2 批 o→2662.4、l→79.05；最后 2662.4÷79.05=33.68。"必须先知道总和"是错觉，除法可以挪到最后。

## softmax 咋算的，不是除根号 d 吗？
- 两次不同的除法：① ÷√d 在 softmax 之前，分数 = q·k/√d，每个分数各自除；② softmax 里 ÷ 所有 e 的总和 → 权重，要看完整行，Flash 挪到最后的是这个。
- 顺序：q·k → ÷√d → 分数 → 取 e → ÷总和 → 权重 → 乘 v 求和。
- 例：d=4，点积 2、6、1、8 → ÷2 → 1、3、0.5、4 → e → 2.72、20.09、1.65、54.60 → ÷79.05 → 0.034、0.254、0.021、0.691。

## l、o 是在 SRAM 存的对吗？
- 对。m、l、o 从这一行开始到算完一直在 SRAM，只有最后 o÷l 写回显存。
- 每行 m、l 各 1 个数，o 128 个数；一个工人管 128 行 ≈ 128×130 个数 ≈ 66KB，装得下（SRAM ~192KB）。
- 一句话：分数用完就扔，只有 m、l、o 在桌上累加，最后除一次写回。

## 我的 FlashAttention 总结（01:48，经修正）
- 每层**每个头**各一张 T×T 表；每格怎么算没变（q·k/√d），Flash 解决的是算出来不用存（在 SRAM 算完马上用掉）。
- 补救是怕 e 的结果超出**数字格式**上限（fp16 最大 65504），和 SRAM 容量无关。SRAM 容量 → 决定 Bc；数字格式 → 决定要减最大值、要补救。
- 标准版："FlashAttention 不让注意力表进显存：切块在 SRAM 算完即用；softmax 分子分母都是加法，分批累加最后除一次；补救是因为减最大值防溢出，而最大值边看边更新。"
- 售前版："不改结果，只改计算顺序，中间表不落显存，注意力快 2~4 倍，长上下文省显存。"

## T×T 表的目的是啥？看每层每个头最关注哪个 token 吗？
- 第 i 行第 j 格 = 这一层这个头里 token i 多关注 token j。目的是马上用：每行权重加权混合 v 得到输出，用完就没用 → Flash 敢不存。
- 每层每个头一张：不同头学不同的关注模式（前一个词、代词指代、标点…），32 个头 = 32 种看法。
- "看最关注哪个 token"是可解释性研究另外存下来画图做的，正常推理不看。

## KV Cache 是存最开始算的 k、v、q 那里吗？
- 存的是每层开始 h@Wk、h@Wv 算出的 K、V（显存里）；不存 Q（只用一次）。
- "最开始" = 每一层的开始，每层各存一份，32 层 32 份。KV Cache = 2 × 层数 × 头数 × 头维度 × token 数 × 字节。

## 长上下文时一行就有 T 个分数，都在 SRAM 里存着吗？
- 不存，哪里都不存。T=32768 时每次只算一批 128 个分数，取 e 加进 l、o 就扔，再算下一批，共 256 批。
- 任何时刻桌上只有当前 128 个分数 + m、l、o；整行像流水"流过"桌面。
- 门口计数器比喻：3 万人排队，屋里每次进 128 个，数完放走。桌子大小和 T 无关，T 长只是多扫几批。

## T×T 是有遮罩的三角形表，第一行就一个，KV 按行切分能理解——那上一条在说啥？
- 三角形：第 i 行 i 个数，最后一行 T 个。长行的分数放哪？就靠 K/V 按行切：每搬一块 K（128 个 token），只算这一行对应的 128 个分数，加进 l、o 就扔。
- "K/V 按行切" = "把一长行分数切成一段段算"，同一件事两个角度。
- T=8、每块 2：第 1 行用块 1 算 1 个；第 3 行块 1 算 2 个 + 块 2 算 1 个；第 8 行分 4 段各 2 个。

## 我懂了：相当于竖着切下来往右移动？（02:29）
- 对。T×T 表上竖着切 = 按 K/V 切块（每竖条一块）；往右移动 = 一条条处理，加进 l、o 就扔；对角线右边遮住的跳过。
- 加分工：横着切给不同工人（每人一块 Q），每个工人在自己横条里竖着一格格往右走。L2 demo 播放动画就是这个。

## 动画演示：K/V 切块后最后一行怎么判断？
- 动画：https://claude.ai/artifact/SGUv7cpAp665dNjNJQr5se （week7/flash-tiles-anim.html）
- 只比块编号（i 横条、j 竖条）：j<i 全算；j=i 对角块算下三角、遮右上；j>i 整块跳过（不搬）。第 i 横条只走 i 块。
- 最后一行 q8：K 块 1~3 全算，K 块 4 对角块里 q8 能看 k7、k8，不遮；被遮的是同块里 q7 看 k8。

## 算完了怎么知道注意力的大小？没存呀
- 推理时不需要：权重是手段，目的是输出 o（已写回）。GPA 比喻：要的是 3.6，不用记每门课占比。
- 训练反向传播：Flash 每行只存 m、l，反向时用 q、k 重算分数，权重 = e^(分数−m)÷l，重算比存大表快。
- 研究可视化：换回普通注意力（如 HF output_attentions=True）。

## 最细版第 1 步就是算这一行的注意力表，后面 softmax、乘 v，再走 norm 流程？
- 对：① 一行分数 → ② softmax 权重 → ③ 混合 v；之后 Wo + 残差 → RMSNorm → FFN + 残差。
- 关键区别：普通做法 ①②③ 是分开的三趟；Flash 每一批 ①②③ 一起做（算 2 个分数 → e 加进 l → e×v 加进 o → 扔），最后除一次。从没有"整行分数都算好"的时刻。

## 切分不是按每行 token，而是按 KV，所以流程我明白了（02:44）
- 对。让 Flash 成立的关键是按 K/V 切（竖条），算完加进 l、o 就扔；按行（Q）切是为了分给工人并行。
- 一句话：竖着切是为了省显存，横着切是为了并行。

## 每个头都这样？最先算出第一行，最后一行最后算出？（03:41）
- 每个头有自己的 q、k、v，各自独立做 Flash，可分给不同工人并行。
- 上面行活少（第 1 横条走 1 块），下面行活多，所以上面常先做完；但行与行独立不排队，真实 GPU 甚至先派活多的行让工人同时收工；这一层要等所有行算完才进下一层。

## 还可以先算 q7、q8 吧，因为反正是加法？
- 可以，但两种"换顺序"原因不同：① 先算哪几行都行 —— 行与行独立；② 同一行先扫哪块 K 都行 —— 这才是因为 l、o 是加法（最大值变了有补救）。

## L3 第一部分练习点评（04:13）
- PAGE=1：并发 55.1、91%；16：55.0、91%；256：49.8、82%（最后一页浪费最多 255 格）。不选 1：页太小 KV 散成碎片，GPU 搬运带宽用不满、页表大（模拟没算这代价）；16 折中，每人最多浪费 15 格。
- 抢占 ≠ 拒绝新请求：房间满了有人要加页时，把最后进来的在住请求请出去重新排队（vLLM 丢掉 KV 重算或暂存 CPU）。朴素不抢占，代价是浪费。
- 售前：原来按最大长度预留，60~80% 空着，只能跑 15 路；分页按实际分配，利用率 90%+，跑 50 多路；搬运受限下 batch 大每步时间几乎不变，一步出的 token 多 3 倍 → 吞吐 ×3。

## L3 第二部分练习点评（04:22）
- 第 1 车跑 6 步，24 座位·步只用 12，浪费 12（取决于最长的 B）。
- 切块后：N 的 TTFT 480→640ms；其他人不叫"decode TTFT"，叫 TPOT（每字间隔），是"变稳"不是"变快"：切块期间 80ms 一字但不卡 500ms，1 秒内字数都约 26。块大小是旋钮。
- 售前满分版：原因 = 长 PDF prefill 一整块算力受限（8000 token ~0.5s）挡住 decode；方法 = --enable-chunked-prefill + --max-num-batched-tokens，规模大可 prefill/decode 分离；代价 = PDF 首字慢 ~30%，切块期间别人 20→80ms 一字，但不卡半秒。

## 周测替换题：为什么 decode 时 Flash 要把 KV 切给多个工人最后合并，prefill 不用？"合并"是什么意思？
- 合并 = 同一行被几个工人分头算，最后把各自的 (l, o)（还有 m）拼成一个答案：分母加分母、分子加分子，最后除。
- 用周测第 2 题：工人 1 l₁=2、o₁=6；工人 2 l₂=2、o₂=16；合并 l=4、o=22 → 5.5。
- prefill 行多，每人领整行自己扫完 → 不用合并；decode 只有 1 行，为了让很多工人一起干只能把这一行切段 → 每人只有半截 → 要合并。
- 一句话：行多按行分（不合并），只有一行就切开分（要合并）。

## decode 注意力表竖着分给工人再拼起来？prefill 表都存着，不也得拼起来、补救吗？
- decode：对，一行竖着切段分给多个工人（段数看上下文长度），最后合并。
- prefill 的表也不存（Flash 两阶段都一样）。
- 补救 ≠ 合并：补救 = 一个工人自己往右走时最大值变了，换算自己的 l、o；合并 = 几个工人各算同一行的一段，最后汇总。同一个公式。
- prefill：每行只有一个工人算 → 只有补救，没有合并；decode：工人内部补救（段比一块长时）+ 工人之间合并。

## prefill 按行分是啥意思？动画演示的是什么？
- 动画（竖着切往右走）演示的就是 prefill。按行分 = 横条：工人 1 领第 1-2、5-6 行，工人 2 领第 3-4、7-8 行；每人在自己横条里一竖条一竖条往右走（竖条 = K/V 块）。
- prefill 两种切法都有：横着分给工人，竖着一块块搬。decode 只有 1 行，没法按行分，只能把这一行切段给多人 → 合并。
